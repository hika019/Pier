# バグ調査手順

症状を消すことは修正ではない。真因が特定できるまでコードを変えない。

## 1. 分類
- **データ破損** (ファイルが壊れた・メタデータが消えた・移動で失われた) → 最優先 (P0)。調査中は該当コマンドを無効化してよい (修正ではなく被害拡大の防止として、理由を明記)。
- **クラッシュ / panic** → P0。
- **Bridge と挙動が違う** → P1。まず skill parity-observation で Bridge の正しい挙動を確定させる。
- **性能退化** → `cargo xtask perf` で前後の数値を取ってから判断する。

## 2. 再現
- 最小再現を作る: 合成ファイル (`pier-testkit`)、コマンド列 (`pier-cli run` またはコントロールチャネル)、OS。
- 再現できないものは修正しない。ログ (`logs/pier.log`)、クラッシュレポート、DB の状態を集めて報告する。

## 3. 真因
- 仮説を立て、反証できる実験 (ログ、テスト、二分探索 `git bisect`) で 1 つずつ潰す。
- 次は真因ではない: 「タイムアウトを伸ばしたら直った」「件数を制限したら直った」「この経路を無効にしたら直った」。
- 同じパターンが他にないか grep で全件列挙する (CLAUDE.md「横展開」)。

## 4. 修正
- 先にセンチネルテストを書き、修正前に fail することを確認する。修正後に pass、修正を revert して再び fail することを確認する。
- panic の修正は「入力 → Err」になる合成回帰テストを付ける。
- ファイル操作・メタデータ書き込みの修正は、障害注入 (書き込み途中の失敗) のテストも付ける。

## 5. 報告
①真因 (1 文) ②根拠 (実験とその結果) ③修正内容 ④センチネルテスト名と revert 時の fail 確認 ⑤横展開の結果 (grep 件数と対応) を報告する。
